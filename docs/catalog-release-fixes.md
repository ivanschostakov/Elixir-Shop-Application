# Исправления магазина после аудита

Сценарий: всё приложение, кроме ИИ-наставника и клиентской Telegram-группы. Пункт 25 (обновление зависимостей) исключён. Изменения в репозитории не означают, что production уже обновлён или что приложение готово отправлять в App Store.

## Что изменено

| № | Исправление | Результат |
|---|---|---|
| 1 | Импорт цены | Выбор единственной цены по ID розничного типа и RUB. Порядок массива не влияет. Без корректной цены вариант архивируется и не продаётся. |
| 2 | Общая математика | Каталожная скидка, затем персональная; округление цены единицы до копейки, затем умножение на количество. Оформление использует ту же формулу. Экспорт распределяет копейки без потери суммы. |
| 3 | Условия МС | Программа и поле «Скидка» контрагента имеют приоритет. Поддерживаются 0%, фиксированные и дилерские 21–25%; локальная шкала и скидка Bitrix не подменяют известное значение МС. Исключения категорий сохраняются. При недоступных свежих условиях оформление останавливается. |
| 4 | Согласие на баланс | API и экран принимают выбранную сумму. В МС передаются согласие и сумма в копейках. Без необходимых настроек списание недоступно. |
| 5 | Точная сумма | Счёт должен соответствовать выбранному списанию. Пример: 46 160 − 4 087 = 42 073 ₽. Другую сумму приложение блокирует. |
| 6 | Проверка документов | Проверяются связанные счета, сумма, валюта/курс, контрагент, организация, связь с заказом, оплата, отмена и отгрузка. Неоднозначность останавливает оплату. |
| 7 | Переходы оплаты | Ключ webhook относится к событию, а не только к PaymentId. «Создан → оплачен» и повтор одного события обрабатываются корректно. |
| 8 | Повторы после отказа | Сохранённый inbox имеет состояние, аренду, количество попыток и дату повтора; worker восстанавливает прерванную обработку. Внешние эффекты вынесены в durable IntegrationRun. |
| 9 | Реквизиты платежа | Проверяются магазин, сумма, валюта и текущая попытка заказа. Одного PaymentStep=OK при опросе недостаточно: проверяется информация о счёте провайдера. |
| 10 | Возврат | Финансовое состояние сохраняется до вызова CRM. Повтор CRM выполняется отдельно. Позднее событие paid не восстанавливает возвращённый платёж. Исправление старых противоречивых is_paid входит в миграцию. |
| 11 | Конкуренция баланса | Блокировка по контрагенту, проверки других незавершённых заказов приложения и МС; блокировка создания оплаты действует через внутренние commit. |
| 12 | Свежая цена | Старый черновик пересчитывается. При изменении цены пользователь получает новый итог и подтверждает его повторно. |
| 13 | Резерв | У авторизованного и гостевого покупателя локальный резерв создаётся под блокировкой. Резерв передаётся в МС и проверяется перед оплатой. Старый снимок остатков не отменяет новый резерв. Ожидаемые поступления не считаются физическим наличием. |
| 14 | СДЭК | Снимок веса из МС, сумма весов всех единиц плюс упаковка, стоимость с копейками. У оплаченного заказа повторная плата за доставку равна нулю. |
| 15 | Гостевой покупатель | Отдельный email покупателя для восстановления, независимый от email получателя. Код и новый пароль возвращают доступ к тому же аккаунту и заказам, старые сессии отзываются. |
| 16 | Обычный вход | Восстановление по email; подтверждение после смены email в профиле. Неверный локальный вход не показывает техническую ошибку конфигурации сайта. |
| 17 | App Attest | Общий срок ожидания iOS-операции 20 секунд, запросов к API — 8 секунд. Зависшая операция освобождает очередь; проверка устройства не обходится. |
| 18 | Изоляция аккаунтов | Полная очистка корзины/черновиков при смене пользователя. Кэш проверяет владельца. Поздние ответы и запросы после смены сессии не попадают в новый аккаунт. |
| 19 | Удаление | Ошибка удаления сохраняет сессию. Успешное удаление очищает локальные данные и файлы аватара; неудачные удаления повторяет существующий worker. |
| 20 | Архив | Архивные варианты недоступны для покупки, включая старую корзину и черновик. |
| 21 | Ошибки | Технический JSON и HTML не используются как текст сообщения покупателю; ошибки полей 422 переводятся в понятные сообщения. |
| 22 | Аватар | Чтение с лимитом 5 МБ, предел 16 млн пикселей, изображение уменьшается до 1024×1024, повреждённые изображения отклоняются. Удаление учитывает .jpeg. |
| 23 | Язык и доступность | Смена языка обновляет заголовки; деньги/даты и имя сохранённой корзины используют выбранную локаль; телефон подписан как телефон для VoiceOver. |
| 24 | Дополнительные награды | Шаблон входящего платежа принимает актуальное имя статуса «Бонусы». Только подтверждённые начисления доступны к списанию. Покупки не запускают второе начисление в приложении. |

## Что требуется перед включением в production

Это не выполнено в рабочем МойСкладе: рабочие документы, роботы и настройки не менялись.

1. Применить миграции `b7d9e1f3a5c7`, `c8e0a2b4d6f8`, `d9f1a3b5c7e9`, `e0a2c4e6f8b0` после существующего head `a6c8e0f2b4d7`, затем развернуть совместимые backend и frontend. Обновление зависимостей не требуется этой задачей.
2. Проверить `MOY_SKLAD_PRICE_TYPE_ID` и `MOY_SKLAD_CURRENCY_ID` в целевой компании; выполнить обычный импорт каталога, чтобы записать новые цены, архив и вес. Пример значений внесён в `.env.example`.
3. Настроить поля/роботов по [контракту МойСклада](catalog-moysklad-contract.md). Только после проверки включать `LOYALTY_SETTLEMENT_CHECKOUT_ENABLED`. Нельзя просто включить флаг со старыми роботами 05/06. После настройки полей перезапустить API и worker.
4. Проверить Redis и существующий `admin_jobs` worker: он повторяет inbox, IntegrationRun и обслуживает резервы. Существующий notification/erasure worker нужен для удаления файлов. Окончательно исчерпанные попытки требуют внимания администратора.
5. Убедиться, что остальные каналы компании учитывают резерв, склад и запрет отгрузки чужих резервов. Локальная блокировка приложения не управляет продажами сторонних систем. Неопределённый результат удалённого POST не освобождает локальный резерв без сверки. Менеджерский заказ с удалённым резервом автоматически не освобождается до подтверждённой отмены. Счёт с неподтверждённым состоянием не освобождает резерв автоматически.
6. В тестовой компании провести связку МС → роботы → Hub → CRM → платёжный провайдер → доставка: отказ/частичное списание, полный баланс, повтор, возврат, последний товар и другой канал продаж. Закрытый код Hub и недоступные роботы 02/08 нельзя считать проверенными по исходникам приложения.
7. Учесть обязательное новое поле `buyer_email` в API гостевого заказа: старые клиенты без этого поля не оформят гостевой заказ. Согласовать совместимое обновление приложения и backend до развёртывания.
8. Проверить установленную iOS-сборку на устройстве, реальную почту, App Attest, VoiceOver и тестовую накладную СДЭК. Подготовить сборку с исключёнными ИИ-наставником и TG-группой отдельно: эта задача их не удаляет.

## Проверки

Итог: **302 проверки backend и 181 проверка frontend прошли**, TypeScript прошёл, проверенный набор изменённых файлов прошёл ESLint без замечаний. Миграции применены к тестовой базе до `e0a2c4e6f8b0`; `git diff --check` прошёл. Тесты выполнялись только на отдельной PostgreSQL `catalog_fixes`, localhost:55461, с тестовыми учётными данными и подменёнными внешними сервисами.

Общий ESLint репозитория не прошёл: 7 ошибок в существующих тестах ИИ/упаковки Yandex Maps и 29 предупреждений преимущественно в экранах доставки вне этой правки. Эти проверки не объявлены зелёными. У pytest остаётся предупреждение о совместимости плагина; зависимости по пункту 25 не обновлялись.

[Результаты проверки](catalog-release-verification-2026-11-21.json) сохранены в Git. Локальные логи находятся в `output/catalog-release-fixes-2026-11-21/` и не входят в коммит. В регрессию входят реальные HTTP/DB-сценарии покупки последних единиц одновременно, возврата при отказе CRM, повторов событий, запоздалого обновления CRM, истечения резерва, неопределённого экспорта, восстановления гостевого аккаунта и удаления аватара; внешние API заменены фикстурами.

Локальная web-сборка запускается, но обычный браузер останавливается на предусмотренном Telegram WebApp gate. Полный покупательский интерфейс этим запуском не проверен; защитный gate не изменялся для тестирования. Проверки iOS на устройстве и production-интеграции остаются отдельными обязательными шагами.

В ходе работы в общем дереве параллельно коммитились другие изменения. Они не отменялись; ИИ-функциональность и зависимости не входят в эту правку.
