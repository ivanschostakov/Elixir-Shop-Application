# Контракт приложения и МойСклада для баланса и резерва

Статус: спецификация необходимых настроек и приёмки. Ни один рабочий робот этим файлом не изменён. Экспортированные конфигурации 05/06 в `output/company-system-review-2026-11-21/robot-configurations` сохранены как свидетельства исходного состояния, они не являются готовыми обновлёнными конфигурациями.

## Данные заказа

- `MOY_SKLAD_BALANCE_CONSENT_ATTRIBUTE_ID`: boolean в заказе покупателя. `false` запрещает любое списание.
- `MOY_SKLAD_BALANCE_AMOUNT_ATTRIBUTE_ID`: long в заказе покупателя, точная запрошенная сумма в копейках. Например, 4087 ₽ передаются как 408700. Ноль при отсутствии согласия.
- Сумма заказа в МС — товары после согласованных скидок плюс доставка. Сумма счёта — сумма заказа минус согласованное списание. Валюта RUB, курс 1, те же организация и контрагент.
- Целочисленные старые поля «Списано бонусных рублей» остаются отображением. Они не заменяют точную разницу сумм и поле запроса в копейках.
- Начисления за покупки и рефералов остаются ответственностью автоматизации МС. Приложение не должно повторно начислять их своим старым ledger.

## Необходимые изменения 05/06

1. Перед запуском проверять явное согласие и положительную целую сумму запроса в копейках. Не списывать баланс лишь по принадлежности к программе.
2. Перечитывать полный заказ, его счета, контрагента, официальный отчёт баланса. Отказ, если запрошенная сумма выше доступного положительного баланса или суммы заказа. Не уменьшать списание молча: клиент должен подтвердить новую сумму заново.
3. Защитить повтор и конкуренцию по контрагенту. Уже созданный согласованный счёт использовать повторно; несколько активных счетов требуют сверки. Проверка флажка до завершения операции не заменяет идемпотентность.
4. Удалить расчёт списания через округлённый процент `var9`. Сформировать позиции счёта с точным итогом в копейках: распределить целевой итог пропорционально исходным суммам позиций, остаток копеек распределить детерминированно. При необходимости разделить одинаковые единицы на две строки с ценой, отличающейся на копейку. Проверить итог по ответу МС.
5. Устанавливать флажки успешного списания только после проверки созданного счёта и точного равенства: `заказ − счёт = запрошенное списание`. Пример: 4 616 000 − 408 700 = 4 207 300 копеек. Прежний счёт 4 207 485 копеек должен быть отклонён.
6. Не менять уже оплаченный/отгруженный заказ, контрагента, организацию и валюту. При сбое после создания счёта повтор должен найти тот же документ и завершить сверку.
7. Согласовать отмену/возврат с Hub: состояние платежа и движение баланса должны соответствовать фактическому возврату. Не создавать обратное начисление вторым независимым механизмом приложения.

Схема импорта обновлённых роботов, транзакционность их блокировок и код Hub не доступны в репозитории. Поэтому автоматически импортируемая «исправленная конфигурация» без проверки в редакторе Роботы 365 не предоставляется.

## Резерв и остаток

Приложение удерживает собственный остаток до подтверждённого экспорта. МС получает `reserve=quantity` для товарных позиций. Перед созданием СБП приложение перечитывает позиции с `fields=stock`, сверяет состав/резерв и достаточность физического остатка для суммарных резервов. Из отчёта для каталога берутся физический остаток минус резервы; ожидаемые поступления не продаются как наличие.

Работу с резервами других каналов и настройку запрета их отгрузки необходимо подтвердить в компании. МС позволяет резервировать будущие поступления; сам факт наличия резерва не гарантирует физический товар. См. [правила резервов МойСклада](https://support.moysklad.ru/hc/ru/%D1%82%D0%BE%D0%B2%D0%B0%D1%80%D1%8B%20%D0%B8%20%D1%81%D0%BA%D0%BB%D0%B0%D0%B4%D1%8B/%D0%BE%D1%81%D1%82%D0%B0%D1%82%D0%BA%D0%B8%20%D0%B8%20%D1%81%D0%B5%D0%B1%D0%B5%D1%81%D1%82%D0%BE%D0%B8%D0%BC%D0%BE%D1%81%D1%82%D1%8C/%D1%80%D0%B5%D0%B7%D0%B5%D1%80%D0%B2%D1%8B) и [JSON API](https://dev.moysklad.ru/doc/api/remap/1.2/).

## Приёмка перед включением

Проверить в отдельной тестовой компании: без согласия; выбранная сумма меньше максимума; дробные копейки баланса; недостаточный баланс; 100% оплаты балансом с доставкой; два заказа одного контрагента; повтор одного запроса; сбой между созданием счёта и флажком; две активные накладные/счета; смена суммы/валюты/организации; оплата и возврат при отказе CRM; последний товар в приложении и другом канале; отрицательное физическое наличие при положительном ожидании; подтверждённая отмена резерва; возврат после отгрузки.

Опрос `getBankCardPaymentState` сам по себе не содержит реквизитов для финансовой сверки. Приложение использует дополнительно [getPurchaseInfo](https://developer.intellectmoney.ru/merchant/api/getPurchaseInfo/). В тестовом магазине нужно проверить фактические поля суммы и комиссию: при несовпадении опрос не признаёт платёж успешным; проверенный webhook остаётся основным каналом финансового подтверждения.
