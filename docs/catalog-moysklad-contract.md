# Контракт приложения и МойСклада для баланса и резерва

Статус: спецификация необходимых настроек и приёмки. Ни один рабочий робот этим файлом не изменён. Экспортированные конфигурации 05/06 в `output/company-system-review-2026-11-21/robot-configurations` сохранены как свидетельства исходного состояния, они не являются готовыми обновлёнными конфигурациями.

## Текущий автоматический режим

По указанию владельца приложение адаптировано к существующим роботам 05/06. Рабочие роботы не менялись. Для подтверждённых программ «Бонусная» (1) и «Партнерская» (2) приложение всегда ожидает расчёт МС, даже при нулевом балансе. Выбор суммы и отказ от списания в интерфейсе отсутствуют. Старые параметры API не позволяют обойти этот режим.

Робот использует доступный баланс как скидку и уменьшает сумму счёта. Приложение передаёт в платёжный шлюз точный остаток по проверенному счёту, не списывает баланс вторым платежом и не дублирует начисления за покупки/рефералов.

- Заказ: товары после каталожной и допустимой персональной скидки плюс доставка. Персональная скидка разрешена только партнёрской программе; бонусная получает предварительный расчёт 5%, без этой скидки. Программа 0 не получает ни одну из этих выгод.
- В счёте проверяются связь с заказом, организация, контрагент, RUB/курс 1, активность, отмена, отсутствие предыдущей оплаты и флаг завершённого расчёта.
- Точное применение баланса = сумма заказа − сумма счёта. Оно не может превышать ни сохранённый доступный максимум, ни актуальный баланс перед оплатой.
- 05/06 округляют процент скидки вниз до 0,01 процентного пункта и сохраняют отдельную целочисленную метку. Для автоматического режима допустимо только объяснимое этим расхождение: `−1 < метка − фактическая разница ≤ заказ / 10000 + 1 + число позиций / 100`. Число позиций учитывает возможное разделение товарных строк при экспорте.
- Пример: заказ 46 160 ₽, счёт 42 074,85 ₽, точная разница 4 085,15 ₽, метка 4 087 ₽. Этот результат текущего робота принимается. Шлюз получает 42 074,85 ₽; метка не становится суммой к оплате. Необъяснимое расхождение остаётся ошибкой.
- Предварительный кешбэк уточняется после расчёта счёта по базе текущего робота: заказ минус доставка минус целочисленная метка списания; отрицательная база даёт ноль. Реальное начисление выполняет МС после отгрузки.
- При нулевом остатке к оплате шлюз не вызывается. При неопределённом состоянии счёта приложение ждёт автоматизацию и не создаёт второй счёт.
- Параметры `MOY_SKLAD_BALANCE_CONSENT_ATTRIBUTE_ID` и `MOY_SKLAD_BALANCE_AMOUNT_ATTRIBUTE_ID` нужны только для уже существующих заказов прежнего явного режима. Для них сохранено точное соответствие выбранной сумме; их правила не ослаблены. Новые автоматические заказы эти поля не отправляют.

Блокировки приложения сериализуют оформление по контрагенту. Сам по себе неотгруженный заказ не блокирует баланс: нужен один действующий счёт на полную сумму, без признаков списания или резерва. Нулевое использование подтверждает завершённый расчёт МС либо, для старого счёта без отметки робота, сохранённый расчёт приложения по тому же заказу. Отмена только в приложении не заменяет сверку документов МС. Если списание положительное или документы не позволяют исключить его, новое списание блокируется с номером заказа. Проверка охватывает и другие каналы; транзакционность самих роботов и Hub этим не доказана.

## Резерв и остаток

Приложение удерживает собственный остаток до подтверждённого экспорта. МС получает `reserve=quantity` для товарных позиций. Перед созданием СБП приложение перечитывает позиции с `fields=stock`, сверяет состав/резерв и достаточность физического остатка для суммарных резервов. Из отчёта для каталога берутся физический остаток минус резервы; ожидаемые поступления не продаются как наличие.

Работу с резервами других каналов и настройку запрета их отгрузки необходимо подтвердить в компании. МС позволяет резервировать будущие поступления; сам факт наличия резерва не гарантирует физический товар. См. [правила резервов МойСклада](https://support.moysklad.ru/hc/ru/%D1%82%D0%BE%D0%B2%D0%B0%D1%80%D1%8B%20%D0%B8%20%D1%81%D0%BA%D0%BB%D0%B0%D0%B4%D1%8B/%D0%BE%D1%81%D1%82%D0%B0%D1%82%D0%BA%D0%B8%20%D0%B8%20%D1%81%D0%B5%D0%B1%D0%B5%D1%81%D1%82%D0%BE%D0%B8%D0%BC%D0%BE%D1%81%D1%82%D1%8C/%D1%80%D0%B5%D0%B7%D0%B5%D1%80%D0%B2%D1%8B) и [JSON API](https://dev.moysklad.ru/doc/api/remap/1.2/).

## Приёмка перед включением

Проверить в отдельной тестовой компании: автоматическое применение баланса при обоих значениях старого параметра согласия; игнорирование старой частичной суммы; нулевой баланс; дробные копейки баланса; недостаточный баланс; 100% оплаты балансом с доставкой; два заказа одного контрагента; повтор одного запроса; сбой между созданием счёта и флажком; две активные накладные/счета; смена суммы/валюты/организации; оплата и возврат при отказе CRM; последний товар в приложении и другом канале; отрицательное физическое наличие при положительном ожидании; подтверждённая отмена резерва; возврат после отгрузки.

Опрос `getBankCardPaymentState` сам по себе не содержит реквизитов для финансовой сверки. Приложение использует дополнительно [getPurchaseInfo](https://developer.intellectmoney.ru/merchant/api/getPurchaseInfo/). В тестовом магазине нужно проверить фактические поля суммы и комиссию: при несовпадении опрос не признаёт платёж успешным; проверенный webhook остаётся основным каналом финансового подтверждения.
