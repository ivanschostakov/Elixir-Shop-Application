# Программы лояльности Elixir Shop

## Выбор программы

Новая версия после подтверждения первой регистрации показывает alert с тремя вариантами:

1. Есть пригласительный промокод — открывается поле ввода.
2. Использовать код компании — партнёрская программа с настроенным фирменным кодом (по умолчанию `Elixir`).
3. Получать 5% бонусами — бонусная программа без пригласительного кода.

Выбор сохраняется через авторизованный `POST /auth/registration-program`. Пропущенный/прерванный выбор восстанавливается при следующем входе: состояние хранится в backend. До выбора новая версия не создаёт контрагента/приветственный платёж и не разрешает расчёт заказа. Новый клиент получает программу, начальную скидку и, при необходимости, приглашение одним созданием контрагента МС. Идентификаторы значений справочников берутся из метаданных, не угадываются.

Существующий контрагент находится по подтверждённой учётной записи. Его программа берётся из МС; alert не показывается, программа/скидка/приглашение в существующей карточке не перезаписываются. Самостоятельная смена через старые операции привязки/отвязки кода для такого клиента блокируется. Неоднозначная личность и недоступная CRM не должны приводить к созданию дубликата.

Для совместимости старые клиенты, не передавшие `select_program_after_registration`, сохраняют прежний путь. Новая форма передаёт этот признак, а выбор делает после регистрации.

## Расчёт выгоды

- Подтверждённая бонусная программа: персональная партнёрская скидка не применяется, даже если в поле скидки МС осталось положительное значение. Предварительно рассчитывается 5% бонусами. Сохранённый пригласительный код не является допустимым состоянием этой программы. Устаревший код/режим в запросе старого клиента не подменяет программу.
- Подтверждённая партнёрская программа: персональная скидка берётся из МС, включая согласованные дилерские значения. Дополнительные 5% не начисляются.
- Программа 0: ни партнёрской скидки, ни 5%.
- Каталожные скидки и исключения категорий учитываются отдельно, тем же расчётом в карточке, корзине и оформлении.
- Начисления за покупки, партнёров и возвраты ведёт автоматизация МС; приложение не создаёт второй кешбэк после оплаты.
- Доступный денежный баланс для программ 1/2 робот применяет автоматически как скидку к счёту. Например, заказ 1 000 ₽ и баланс 200 ₽ → к оплате 800 ₽. Покупатель не выбирает частичную сумму до изменения механики роботов.
- Точные проверки, округление и резерв описаны в [контракте МС](catalog-moysklad-contract.md). Показанный кешбэк предварительный; реальное начисление выполняется после отгрузки.

Шкалы реферальных вознаграждений, месячные ограничения и расчёт второго уровня в историческом локальном/Bitrix механизме не являются доказательством действующих настроек МС. Известная программа и личная скидка МС имеют приоритет.

## Дополнительные начисления приложения

- Новый клиент получает 1 000 приветственных ₽ при первом подтверждении почты в мобильном приложении. Выбор программы и первая оплата не требуются. Уже выданный приветственный бонус не дублируется.
- В течение 120 часов остаток автоматически уменьшает цену товаров после прочих скидок максимум на 50% (с округлением вниз до копейки). Доставка исключена. Пример: товары 799,99 ₽ и доставка 200 ₽ → скидка 399,99 ₽, к оплате 600 ₽. После срока неиспользованный остаток недоступен.
- Это отдельная скидка магазина: сайт и менеджеры не могут её потратить. Сумма фиксируется в заказе; в МС экспортируются уже уменьшенные цены товаров, а не бонусный платёж. Лимит не относится к обычному балансу МС.
- Исторические приветственные начисления и награды за отзывы проводятся отдельными входящими
  платежами на контрагента: статус «Бонусная (Накопительная)», валюта «б.руб»,
  НДС 0, дополнительное поле «Тип платежа» = «Бонусная». Платёж не привязывается
  к заказу или отгрузке через `operations`.
- Через 3 дня после оплаченного заказа отправляется одно напоминание об отзыве;
  оно открывает первый товар заказа, на который пользователь ещё не оставил
  отзыв.
- Текстовый отзыв подтверждённого покупателя даёт 100 бонусов, отзыв с фото —
  200 бонусов всего. За один товар награда выдаётся один раз.

## Техническая реализация

- МойСклад остаётся источником денежного баланса контрагента.
- Локальный реестр `loyalty_bonus_credits` хранит источник и идентификатор
  входящего платежа `moysklad_paymentin_id`. У новых проводок `expires_at` пустой.
  Старые идентификаторы нативной бонусной системы сохраняются для сверки.
- Идемпотентные ключи не позволяют повторной обработке оплаты, регистрации или
  отзыва задублировать бонусы.
- Фоновый обработчик повторяет неудачные приветственные начисления и награды за
  отзывы. `externalCode` и постоянный `syncId` защищают от повторной проводки.
  Найденное ручное приветственное начисление с той же суммой требует сверки.
- Уже проведённые нативные бонусы автоматически в денежный баланс не копируются.
  Начисления за покупки и партнёров, возвраты и списания выполняет общая система
  учёта МойСклад; приложение не дублирует её платёжные документы.
- Ожидающие синхронизации начисления не прибавляются к доступной сумме.
- МС определяет программу и личные условия существующего клиента. Сайт подтверждает тип нового промокода; его `lookup` должен возвращать `is_firm_promo` и `referral_owner_id`. Для нового партнёрского выбора нужно развернуть обновление `integrations/bitrix/elixir.promo/lib/Service/PromoService.php`.
- `GET /admin/referrals/settlements` разделяет зачисления в депозит, внешние
  перечисления и нерассчитанный остаток. Внешнее перечисление регистрируется
  идемпотентным `POST /admin/referrals/settlements/transfer`.
- Пользовательская refresh-сессия скользящая и действует 365 дней; временная
  ошибка сети не удаляет локальные токены. Административная сессия — 30 дней.

## Настройки

| Переменная | По умолчанию |
| --- | ---: |
| `LOYALTY_ORDER_CASHBACK_PERCENT` | 5 |
| `LOYALTY_COMPANY_PROMO_CODE` | Elixir |
| `LOYALTY_TEXT_REVIEW_BONUS_POINTS` | 100 |
| `LOYALTY_PHOTO_REVIEW_BONUS_POINTS` | 200 |
| `LOYALTY_BONUS_LIFETIME_DAYS` | 60 |
| `LOYALTY_EXPIRY_WARNING_DAYS` | 14 |
| `NOTIFICATION_REVIEW_REMINDER_AFTER_DAYS` | 3 |
| `USER_REFRESH_TOKEN_LIFETIME_DAYS` | 365 |

В релизе постоянно используется схема денежного баланса; учёт, оплата с баланса
и синхронизация заказов не переключаются через переменные среды.
`MOY_SKLAD_BONUS_PAYMENT_TEMPLATE_ID` задаёт ID согласованного накопительного
входящего платежа. Из него берутся только организация, статус, валюта и
метаданные нужных дополнительных полей; клиент, сумма, назначение, комментарий
и ключи идемпотентности формируются для конкретного начисления.

`MOY_SKLAD_BONUS_PROGRAM_ID`, сроки сгорания и нативный бонусный кошелёк остаются
только для чтения исторических данных прежней модели
баланса. В продакшене этот старый режим включать не следует.

## Проверки этой правки

[Результаты регрессии](loyalty-registration-verification-2026-11-21.json): изолированная тестовая база, все внешние API подменены. Рабочие данные МС не менялись. Проверка нативного alert и остальных экранов на физическом iOS-устройстве не выполнялась. PHP runtime локально отсутствует, поэтому обновление `PromoService.php` не проверялось запуском PHP.

При подготовке коммитов расширенная backend-регрессия дала 334 успешные проверки
и 8 падений. Все 8 воспроизведены на отдельном снимке исходного `HEAD` (`974bd0a`),
поэтому этот расширенный набор не объявлен полностью зелёным. Frontend: 186 тестов,
TypeScript и полный ESLint с `--max-warnings 0` прошли.
