# Elixir Promo для 1С-Битрикс

Модуль делает Bitrix единственным источником истины по промокодам. Приложение не читает базу Bitrix напрямую и не хранит у себя копию правил скидок.

## Возможности

- защищённая проверка существования и активности купона;
- расчёт скидки штатным механизмом корзины Bitrix;
- точное повторение режимов сайта: собственный код, сохранённый код реферера,
  фирменный и внешний купон;
- сохранение/смена реферера в `UF_PARENT_ID` из приложения с защитой от
  собственного кода и циклических связей;
- расчёт прямых и двухуровневых реферальных начислений без записи начислений
  или бонусных операций в Bitrix;
- идемпотентный учёт прогресса оплаченных покупок приложения в Bitrix, чтобы
  сумма личных покупок и персональная скидка совпадали на сайте и в приложении;
- проверка месячных условий реферера; журнал начислений и статусы
  `pending`/`approved`/`rejected` хранятся только в PostgreSQL приложения;
- расчёт по конкретным товарам/предложениям и количеству;
- сопоставление по числовому ID, `XML_ID` варианта, артикулу или `XML_ID` родительского товара;
- автоматическое создание купона при заполнении `UF_PROMO` и выдача собственного
  кода при достижении 100 000 ₽ личных покупок;
- API token, IP allowlist и rate limit;
- русские и английские человекопонятные сообщения API.

## Требования

- 1С-Битрикс;
- PHP 8.1+;
- установленные модули `sale`, `catalog`, `iblock`;
- HTTPS;
- товары приложения должны иметь `system_id`, совпадающий с `XML_ID` товара или торгового предложения Bitrix;
- закрытый каталог вне `public_html`, доступный на запись пользователю PHP-FPM.

## Установка

1. Скопировать каталог `elixir.promo` в:

   ```text
   <DOCUMENT_ROOT>/local/modules/elixir.promo
   ```

2. Установить модуль в административной панели:

   ```text
   Marketplace → Установленные решения → Elixir: промокоды и скидки
   ```

3. Открыть настройки модуля и проверить:

   - ID правила скидки;
   - ID инфоблоков товаров и предложений;
   - ID сайта, типа плательщика и валюту;
   - закрытый служебный каталог;
   - IP backend-сервера.

4. Сгенерировать отдельный API-секрет:

   ```bash
   openssl rand -hex 32
   ```

5. Сначала оставить API и автоматическое создание выключенными.

## API

Endpoint:

```text
POST https://<домен>/bitrix/tools/elixir.promo/api.php
X-Elixir-Promo-Token: <API_TOKEN>
Content-Type: application/json
```

Проверка промокода:

```json
{
  "action": "lookup",
  "promo": "PROMO-CODE"
}
```

Расчёт корзины:

```json
{
  "action": "quote",
  "promo": "PROMO-CODE",
  "user_email": "customer@example.com",
  "items": [
    {
      "variant_system_id": "UUID-ВАРИАНТА",
      "product_system_id": "UUID-ТОВАРА",
      "sku": "АРТИКУЛ",
      "quantity": 2
    }
  ]
}
```

Получение контекста скидки покупателя:

```json
{
  "action": "context",
  "promo": "PROMO-CODE",
  "user_email": "customer@example.com"
}
```

Получение актуального профиля программы без обязательного промокода:

```json
{
  "action": "profile",
  "user_email": "customer@example.com"
}
```

Операция возвращает собственный промокод, закреплённого реферера и его
промокод, сумму покупок, текущий процент и группы. Backend приложения использует
её при открытии профиля и корзины, чтобы Bitrix оставался источником истины.

Сохранение или смена реферера:

```json
{
  "action": "attach_referrer",
  "promo": "PROMO-CODE",
  "user_email": "customer@example.com"
}
```

При смене реферера Bitrix сбрасывает прогресс текущей реферальной связи и
удаляет старую группу персональной скидки. Собственный промокод покупателя
применить нельзя.

Расчёт начислений без изменения данных Bitrix:

```json
{
  "action": "quote_referral_accrual",
  "external_order_id": "EP-ABC12345",
  "user_email": "customer@example.com",
  "promo": "PROMO-CODE",
  "amount": "12500.00",
  "currency": "RUB",
  "paid_at": "2026-07-28T12:00:00+00:00"
}
```

Ответ содержит получателей первого и второго уровней, проценты, суммы и снимок
условий за месяц. Операция не создаёт в Bitrix заказ, начисление, запись
бонусного счёта или служебный элемент инфоблока.

После сохранения расчёта в PostgreSQL приложения backend отдельно фиксирует
прогресс оплаченной покупки:

```json
{
  "action": "record_paid_purchase",
  "external_order_id": "EP-ABC12345",
  "user_email": "customer@example.com",
  "promo": "PROMO-CODE",
  "amount": "12500.00",
  "currency": "RUB",
  "paid_at": "2026-07-28T12:00:00+00:00"
}
```

Пара `source + external_order_id` уникальна: повторный webhook возвращает уже
созданную запись и не увеличивает сумму личных покупок второй раз. В Bitrix
хранится только этот технический прогресс покупки — он нужен для общей суммы
покупок и одинаковой персональной скидки на сайте и в приложении. Сам журнал
начислений, его суммы и статусы в Bitrix не записываются.
При первой успешной фиксации оплаченного заказа модуль атомарно увеличивает
стандартный `USE_COUNT` купона Bitrix. Поэтому штатная статистика применения
промокода объединяет оплаченные использования с сайта и из приложения.
Повторная доставка webhook не увеличивает счётчик ещё раз.
В настройках модуля Bitrix показывается отдельная таблица по приложениям:
промокод, количество оплаченных заказов, уникальные покупатели, сумма заказов,
общий счётчик применений Bitrix и дата последней оплаты.
Если фиксация прогресса временно не прошла, worker приложения повторяет её
идемпотентно; успешная оплата заказа из-за сбоя интеграции не отменяется.

Реферальный расчёт создаётся в приложении только при фактическом применении
чужого персонального кода. Фирменный `ELIXIR` и обычные скидочные купоны дают
скидку, но не создают начисление старому закреплённому рефереру.

Для закрытия месяца действуют правила программы:

- пожизненная сумма личных покупок получателя — не менее 100 000 ₽;
- личные покупки получателя в расчётном месяце — не менее 10 000 ₽;
- первый уровень получает `max(3%, P − N)`;
- второй уровень получает фиксированные 3%;
- Bitrix возвращает итог проверки через `referral_eligibility`;
- приложение переводит собственную запись из `pending` в `approved` или
  `rejected`; повторная обработка не создаёт дублей.

Проверка закрытого месяца:

```json
{
  "action": "referral_eligibility",
  "period": "2026-07",
  "user_id": 396
}
```

Для совместимости при поэтапной выкладке сохранена операция
`record_paid_order`: она объединяет расчёт и фиксацию прогресса покупки, но
также не записывает начисления в Bitrix.

Если передан `user_email`, модуль ищет активного покупателя Bitrix. При отсутствии
совпадения расчёт выполняется как для анонимного покупателя и явно возвращает
`user_context: "anonymous"`. Числовой `user_id` Bitrix также поддерживается.

Клиентское приложение не обращается к endpoint напрямую. Запрос выполняет только backend приложения, а token никогда не попадает в мобильную сборку.

## Исторические пользователи

Автоматическое создание работает при новой регистрации или изменении `UF_PROMO`.
Если до установки модуля уже существовали пользователи с `UF_PROMO`, их проверяют
один раз до запуска. Постоянного или публичного endpoint массовой синхронизации в
модуле нет.

## Ввод в эксплуатацию

1. Проверить PHP-синтаксис файлов на сервере.
2. Установить модуль с выключенными функциями.
3. Заполнить настройки и tokens.
4. Проверить `lookup` на активном и несуществующем коде.
5. Проверить `quote` на тестовой корзине и сравнить результат с корзиной сайта.
6. Включить API.
7. Переключить backend приложения.
8. Повторить контрольный заказ.
9. Только после этого включить автоматическое создание купонов.

## Production backup

Перед изменением данных Bitrix обязательно создаётся и проверяется полный дамп
базы и архив затрагиваемых файлов. Бэкап production не относится к временным
артефактам и после выкладки не удаляется.

## Откат

- выключить API и автоматическое создание в настройках;
- вернуть backend приложения на прежний режим;
- удалить модуль через административную панель;
- созданные купоны автоматически не удаляются.
